# Design

## Context

The prune runs outside the sandbox from the SessionStart and Stop hooks and the terminal shell task. Its files live in the git common dir: `coldlogic-prune.log`, `.stamp`, `.kept`, and the `coldlogic-prune.lock/` directory with its `pid` file. A session started in the main checkout can write that dir: the sandbox allows writes under the launch directory, and Claude Code's own mandatory denies there cover only `.git/hooks` and `.git/config` (see "Sandbox finding"). Before this change the script read the lock's `pid` without a check (its first line can reach the log), appended to the log and redirected the detached run into it with `>>`, touched the stamp with plain `touch` (which follows a link, and makes the target of a dangling one), wrote the kept file and the trimmed log to `<file>.tmp.$$`, read the kept file without a check, and wrote the lock's `pid` file with `>`.

## Goals / Non-Goals

**Goals:** no write, read-back or touch of the prune's own files goes through a link or lands in a file that isn't a regular one of the user's with one name; no log line carries a live `$( )` or backquote; a run that can't log removes nothing (decision 1).

**Non-Goals:** making bash open files with `O_NOFOLLOW` (it can't); defending against a common dir that is itself a link; git configuration a session can write (see "Sandbox finding").

## Decisions

1. **Open the log once, after checking it.** `open_log` makes the log with noclobber (`O_EXCL`, which fails on any link, a dangling one too) and umask 077 when nothing is there, then opens it for appending on one file descriptor only if it is `own_file`: `-f`, not `-L`, `-O`, and a link count of 1 (a hard link would let the append reach another file). When it isn't, the run **fails closed**: one line on stderr and no removal, exit 0 (a `--background` run doesn't detach). A removal with no restore record is worse than a removal skipped; the next run, once the log is fixed, does it. A dry run writes nothing, so it never opens the log, and the kept-file logic is unchanged. `say()` and the detached run's stdout and stderr use that descriptor. One check and one open per run replace a check before each line, so there is one race window instead of one per line.
   `say()` opens the log again, with the same checks, when the path no longer names the open file (`[ "$log" -ef /dev/fd/$log_fd ]` fails). Another run's trim renames a new file over the log, and a run that opened it before (one that skips because the lock is held, say) would otherwise write into the orphaned old file, and its kept-file entry would stop the line from ever being logged. *Alternative:* trim in place under the lock; rejected as no better: both approaches have a window between `mapfile` and the rename (or the truncate), in which a line another run appends is lost (see Risks). Should the reopen fail, the line is dropped (`/dev/null`) and `log_line` reports it.
   **Intent before removal.** Each worktree removal and branch deletion first writes `removing worktree ...; to restore: ...` or `deleting branch ...; to restore: ...` (`intend`, which fails when `log_line` can't record it). When it fails, the removal is skipped and kept for the next run, so a removal made after the log went bad (swapped for a link mid-run, say) has no gap in its record. The `removed ...` / `deleted ...` line still follows a success, and a failed removal keeps its failure line after the intent. `git worktree prune` writes an `unregistering worktree ...` intent for each gone worktree first, and is skipped when it can't. Trimming keeps an intent line like a removal, since it is the only record when the `removed ...` line after a made removal couldn't be written, unless a later line says the same: that removal's line, or the same intent again (a removal that keeps failing writes one every run). Those redundant ones are dropped with a trim, or once there are over 100 of them, so the log can't grow for good. A reason `keep` couldn't log is left out of the kept file, so the next run logs it. The stamp, like the other files, is read only when `own_file`: a link or another user's file counts as no stamp, and the next run replaces it.
   `own_file` and `mtime` (and `device()`) use GNU `stat` only. The BSD `stat -f` fallbacks were dead code: `packages/prune-worktrees.nix` puts coreutils in `runtimeInputs`, and the script already needs GNU `mv -fT` and `realpath -m`.
   *Alternative:* check before every append, as the issue suggests. Same check, more windows, a `stat` fork per line.
2. **Rewrite through `mktemp`, rename with `mv -fT`.** `replace_file` writes stdin to `mktemp "<file>.XXXXXX"` (made under umask 077, so a strict umask can't leave it unwritable) and renames it over the file. Rename replaces a link rather than following it; `-T` keeps it from moving into a directory planted at the name. The stamp, the kept file and the trimmed log use it. When `mktemp`, the write or the rename fails, it still reads all of stdin, and both pipelines into it end in `|| true`: otherwise the writer (the trim's, with up to 1000-odd lines) dies of SIGPIPE, and under `pipefail` and `set -e` the run would exit non-zero.
3. **Read back only own files.** The kept file and the lock's `pid` are read only when `own_file`, and the log is trimmed only when this run opened it and it is still `own_file`. A run skipped for the lock writes the last run's reasons back, and logs the lock's owner; reading either through a link would copy a file the sandbox can't read (say `.env`) into one it can. A `pid` that isn't `own_file` counts as no owner recorded: the lock is taken over once over an hour old, and the exit trap, finding no token of its own, leaves it.
4. **noclobber for the lock's owner, a rename for the stamp.** The lock directory was just made by this run, so a `pid` file in it can only be a link planted since; noclobber refuses it, and the run takes the existing "owner can't be written" path. The stamp is replaced with a new empty file (`mktemp`, then `mv -fT`, without `replace_file`'s stdin copy) rather than touched, so neither a symbolic nor a hard link there has its target's time changed.
5. **Quote names with `q` (`printf %q`), clean free text with `clean`.** Every path, branch, base ref and default branch that reaches a log line is quoted where the message is built, so the fixed wording stays readable and only the names are escaped. A git error or a lock owner is free text, which `%q` would turn into a backslash before every space; `clean` instead replaces control characters (newlines included) with spaces, turns a backquote into `'` and `$(` into `$ (`. The keys the kept file is matched on are unchanged, but a reason whose text changed logs each existing kept entry once more.

## Sandbox finding

Read-only, from this session's sandbox settings and Claude Code 2.1.322's bundle; nothing was written into a real `.git`.

- Claude Code adds mandatory write denies relative to the directory it was launched in: `<cwd>/.git/hooks`, `<cwd>/**/.git/hooks/**`, and `<cwd>/.git/config`, `<cwd>/**/.git/config` (unless git config writes are allowed). A session launched in the main checkout, as this one was, therefore can't write the main `.git/hooks` or `.git/config`. A probe in a throwaway repo under `$TMPDIR`, outside the launch directory, could write all three, so the denies don't apply beyond it.
- `.git/coldlogic-prune.*` and `.git/worktrees/<name>/` match none of them and are writable from a session in the main checkout. That is the hole this change closes for the log.
- Wider: `.git/worktrees/<name>/config.worktree` is writable too, and the module sets `extensions.worktreeConfig`, so git reads it. A session could set `core.fsmonitor` (or `core.hooksPath`) there, and the prune's own `git status` in that worktree, run outside the sandbox, would execute it. A narrow deny, `${mainCheckout}/.git/worktrees/*/config.worktree` in `sandbox.filesystem.denyWrite`, would close it, but `coldlogic:worktree-hooks-path` writes that file from a session's `devenv shell` on a new worktree's first shell, so the deny needs that task moved (or run only from hooks) first. Not done here: filed as coldlogic-devenv#97.
- A session launched in a linked worktree gets these denies under that worktree, not the main checkout; whether it can write the main `.git` then depends on whether the main checkout is in its allowWrite (the module doesn't add it).

## Risks / Trade-offs

- **[Check-to-open race]** Bash can't open with `O_NOFOLLOW`, so a process racing the run can swap a link in between the check and the open, or between `mktemp` and its write. → One window per run for the log, microseconds wide, and the attacker has to win it while the hook runs. The guardrails here are for mistakes and casual abuse, not a determined local attacker.
- **[The common dir a link]** `$common` is what `git rev-parse --git-common-dir` returns; a session could point a worktree's `commondir` file elsewhere. → Every name the run writes there is a fixed `coldlogic-prune.*` name it creates or replaces by rename, so it can't append to an existing file such as `~/.zshrc`. Out of scope.
- **[Not-owned case untested]** A log owned by another user can't be made without root, so `-O` is covered by review only. The FIFO, directory and hard-link cases cover the rest of `own_file`.
- **[Children inherit the log's descriptor]** Bash can't set close-on-exec, so every child (git, lsof, gh-app, timeout) holds `log_fd` open. None writes to it: their output is captured or sent to `/dev/null`, and only the detached run's own stdout and stderr go to the log. → A hung child keeps the old file's inode alive after a trim renames a new log over it, and anything sent to the old descriptor then is lost. Acceptable; closing it (`{log_fd}>&-`) on each of the many git calls isn't worth the clutter.
- **[The log is made eagerly]** A run makes the log (empty) before it knows it will log anything. Opening it on the first write would leave the detached run's stdout nowhere to go, and every session's hooks start one anyway. Left as is.
- **[Trim race]** `trim_log` reads the log with `mapfile` and renames the rewrite over it: a line another run appends in between is lost. Only a run skipped for the lock appends while another holds it, and only once per change of reason, so the window is rare. Accepted.
- **[A failed removal's intent stays]** A removal that fails once and is never retried the same way (removed by hand, say) keeps its `removing ...` line, followed by its failure line, for good. → One line per distinct failure, which the failure line explains. Accepted.
- **[`git worktree prune` beyond the list]** It also deletes admin dirs `git worktree list` doesn't show (a missing `gitdir` file), which get no intent line. Predates this change; out of scope.
- **[A log that goes bad mid-run is silent]** The stderr line comes only from the start check; a later failure skips removals and logs nothing. The next run's start check reports a log that stays bad. Accepted.
- **[Log wording]** Names with shell characters now read escaped (`feat\]x`), and a kept reason whose text changed (every one with a git error or lock owner, now cleaned rather than quoted) is logged once more after the update.

## Migration Plan

None. Projects get it on their next lock bump. An existing log, stamp and kept file are regular files of the user's and keep working.
