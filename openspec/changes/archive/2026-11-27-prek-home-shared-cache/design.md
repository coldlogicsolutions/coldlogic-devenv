# Design

## Context

Checked in the code:

- devenv's `src/modules/integrations/git-hooks.nix` at the locked rev (`e874a14853d5bbf7ff43acd25960dbf9dc2f3e45`, `devenv.lock`), inside `lib.mkIf cfg.enable`, sets `env.PREK_HOME = "${config.devenv.state}/prek";` at plain priority (no `mkDefault`), and `enterShell = lib.mkAfter ''mkdir -p "$PREK_HOME"'';`.
- The installed hook (`<main checkout>/.git/hooks/pre-commit`, written by prek 0.5.11) sets no environment. It execs `prek hook-impl ... --config=.pre-commit-config.yaml`, so prek uses whatever `PREK_HOME` the committing process has.
- `devenv.nix` already reads the home directory with `builtins.getEnv "HOME"` (`gnupgHome`, and `XDG_RUNTIME_DIR = "${builtins.getEnv "HOME"}/.cache/devenv/run"` in `claude.code.env`). devenv evaluates impurely, so this is the user's home.
- The sandbox's `allowWrite` already holds `"~/.cache/prek"` (`devenv.nix`, `sandbox.filesystem.allowWrite`), and the session-permissions spec already requires the prek cache be writable.
- `config.git-hooks.enable` is already read in the developer module (`hooksExpected`).
- devenv's `src/modules/top-level.nix` (same rev) declares an internal `assertions` option and fails the shell's evaluation on any failed entry. The module doesn't use it yet; its existing self-checks use `lib.assertMsg` in `let` bindings.

Assumed, not reproduced: the failing commit was a bare `git commit` that inherited the main checkout's `PREK_HOME` from the shell that started `claude` (the wrapper starts the real `claude` with the shell's environment). The fix holds either way: the value is the same in every checkout and the sandbox allows it.

## Goals / Non-Goals

**Goals:** a commit from any checkout or worktree, in a session or a terminal, bare or through `devenv shell`, finds prek's state somewhere it can write.

**Non-Goals:** changing how sessions run commits; changing the sandbox or permission rules; cleaning up the old `.devenv/.../state/prek` directories.

## Decisions

- **Override with `lib.mkForce`, in the developer profile module.** devenv's definition is plain priority (100); a second plain definition of a different string would be a conflicting-definitions error, so the module uses `lib.mkForce` (priority 50), which wins. It is guarded with `lib.mkIf config.git-hooks.enable`, mirroring devenv's own condition, so a project with hooks off gets no stray variable. Alternative considered: `mkOverride` with a custom priority. No reason to pick a number; `mkForce` is the conventional spelling.
- **`"${builtins.getEnv "HOME"}/.cache/prek"`, as the module already derives home paths.** It matches the sandbox's `~/.cache/prek` entry and prek's own default (prek falls back to `~/.cache/prek` when `PREK_HOME` is unset). Alternative: `XDG_CACHE_HOME`; rejected because the sandbox entry is literally `~/.cache/prek`, and a different `XDG_CACHE_HOME` would land outside it.
- **Leave devenv's `mkdir -p "$PREK_HOME"` alone.** It runs after the variable is exported, so it now creates `~/.cache/prek`, which is writable in a terminal and allowed in a session.
- **Alternative rejected: unsetting `PREK_HOME` in the hook or the wrapper.** The hook is generated by prek and shared by all worktrees; the wrapper would cover only sessions it starts. One environment value covers every path into a commit.
- **Tested by an entry in devenv's `assertions` option, beside the definition.** devenv's `top-level.nix` (same rev) declares `assertions` (a list of `{ assertion; message; }`) and throws on any failed one when the shell is evaluated, so the gate's existing `devenv build shell` steps and fixture `developer` builds check it, with no change to `scripts/check.sh`. The entry, guarded like the definition by `config.git-hooks.enable`, compares the merged `config.env.PREK_HOME` with a `prekHome` binding the definition also uses. Reading `config.env` there doesn't recurse: nothing in `env` depends on `assertions`. It catches the definition being removed or losing to devenv's, and a project overriding it at a higher priority. Alternatives rejected by the user: a gate step through `devenv eval`, and a manual check only.

## Risks / Trade-offs

- [Shared state across checkouts: prek's hook environments and lock are now one per user, not one per checkout] → that is prek's own default layout; it takes a lock at its root for concurrent runs.
- [Running sessions keep the old inherited `PREK_HOME` until restarted] → noted in the proposal's rollout line and the PR description.
- [A project that sets `PREK_HOME` itself is now overridden, or, at a higher priority than `mkForce`, fails the assertion] → none of the fixtures or profiles set it, and the requirement is that every developer shell uses the shared cache.
- [The assertion compares against the same `prekHome` binding the definition uses, so a wrong path in that binding passes] → the binding is one literal, reviewed with the change; the assertion guards the override's presence and priority, which is what can silently regress.
- [The first commit after the change rebuilds hook environments in `~/.cache/prek`] → one-time cost; the old directory is unused and can be removed by hand.
