# Design

## Context

`protectedFiles` is the generated settings path and `.mcp.json`. `sessionCannotRelink` is the status of both `devenv:files` and `devenv:files:cleanup`. In a session, for each protected file that is missing or a stale link, it runs `ln -sfn "$want" "$f"`. If any relink fails, it exits 0 and devenv skips both tasks. Otherwise it exits 1 and they run. They then find the links current and leave them alone. `ln -sf` is not atomic: it unlinks the old link and then calls `symlink(2)`. In #68 the sandbox let the unlink through and denied the create, so the probe deleted the very link it meant to protect. See proposal.md for the impact.

devenv 2.4's scripts (read from the task's store paths, `/nix/store/…-devenv-files` and `/nix/store/…-devenv-files-cleanup`):

- `devenv:files` writes every file it manages to `.devenv/profiles/<profile>/state/files.json` (`managedFiles`) under the name it was configured with. The settings path is configured as an absolute path (`<root>/.claude/settings.json`), `.mcp.json` as a relative one.
- `devenv:files:cleanup` runs before it. For each recorded entry that isn't an exact string in its `currentFiles` list, it builds `$root/$entry` and `rm`s it if it is a link into `/nix/store`.

## Goals / Non-Goals

**Goals:** no shell in a session ever leaves a protected path missing. The sandbox, not a guess, still decides whether a session may relink.

**Non-Goals:** changing devenv's own `devenv:files` script; working around Claude Code's reverting of protected paths around tool calls; making the relink succeed where the sandbox denies it.

## Decisions

1. **Keep the probe, make it atomic.** For each protected file that needs it, the probe runs `ln -s "$want" "$tmp"` with `tmp="$(dirname "$f")/.$(basename "$f").coldlogic-relink.$$"`, then `mv -f "$tmp" "$f"`. `mv` within one directory is `rename(2)`, which swaps the directory entry in one step. If either step fails, it runs `rm -f "$tmp"` and adds the file to the stale list. The old link is never unlinked on its own, so whether the sandbox denies the create, the rename, or both, the path keeps resolving to its old target. A missing link takes the same path: `mkdir -p` the parent, then link and rename.
   *Alternative:* in a session, never relink protected files and only report them. It is simpler and never writes near a protected path. It was rejected because it throws away #47's property: when the sandbox allows the write (sandbox off, or a path the session's config doesn't deny), the session fixes the link itself instead of nagging. It would also mean guessing what the sandbox allows. With the atomic rename, a denied relink costs nothing, so there is no reason to give that up.
2. **Don't rename over a directory.** `mv -f tmp f` moves into `f` when `f` resolves to a directory. The probe already skips paths that exist and aren't links. It now also treats a link that resolves to a directory as stale without touching it. The module never generates one, so this only guards against a hand-made mess.
3. **Package the probe as a script with a build-time test.** `packages/session-relink.sh` takes `[--check-only] [--print] [--state <files.json>] <path> <target> [<path> <target> ...]`, works relative to the current directory, exits 1 when a task may run and 0 when it should be skipped (some file is stale and couldn't be relinked). Any other exit is an error: 2 for bad usage, and 3 when a command fails, through an ERR trap, with explicit exits where bash ignores the trap (inside `if` conditions). Both status scripts in `devenv.nix` run their task only on an explicit 1. Any other result, a failed `cd "$DEVENV_ROOT"` included, skips it. Both tasks would fail open otherwise: cleanup unlinks, and `devenv:files`' own `ln -sf` is the deletion #68 saw. Outside a session the status still exits 1. A path that exists and isn't a link is never stale, in any mode: it is left to `devenv:files` to report, and it neither skips cleanup nor appears in the notice. `--check-only` only compares, with no relink and no sweep. `--print` prints the stale paths. `coldlogic:generated-files-stale` uses `--check-only --print`, so the notice and the skip decision share one comparison. `packages/session-relink.nix` wraps it with `writeShellApplication` (coreutils, findutils, jq) and runs `packages/session-relink-test.sh` against the raw script in the build, as `claude-guard.nix` does. A failing test fails the shell's build. In `devenv.nix`, the status keeps the `CLAUDECODE` check and `cd "$DEVENV_ROOT"`, then calls the script. That way the logic can be tested without a session or a sandbox: the test simulates a denied create with a read-only directory, and a denied rename with a `mv` shim on `PATH` that fails.
   *Alternative:* keep it inline in `devenv.nix` and test by evaluating it. That would need a devenv evaluation in the test, for no gain.
4. **Guard cleanup against a respelled protected file.** Is the risk real? Not today: both `managedFiles` and `currentFiles` use the same string for each protected file (absolute settings path, relative `.mcp.json`), so cleanup skips them. It would become real if the recorded spelling of a protected file ever differed from the current one, for example if a devenv or module update moved `settingsPath` from absolute to relative or back. Then cleanup would see the old entry as an orphan, resolve `$root/<entry>` to the live link, and `rm` it. A plain unlink is exactly what the sandbox let through in #68. A moved checkout is harmless: an old absolute entry becomes `$root//old/path`, which doesn't exist. So `devenv:files:cleanup`'s status passes `--state` with the profile's `files.json` (`config.devenv.state`, the path devenv's cleanup script reads). For each recorded entry that differs from a protected file's current name but names the same path, the script exits 0. A current name is made absolute with `$PWD/` when relative. So that the check doesn't depend on how devenv joins an entry to the checkout, an entry is read both ways: as `$PWD/<entry>` (what devenv 2.4's cleanup builds), and as it is when it starts with `/`. Either match skips. All paths are normalised with `realpath -ms`, which collapses `//`, `.` and `..` without resolving any link, so `.claude//settings.json` and `x/../.claude/settings.json` match too. This makes an absolute recorded settings path with a relative current name skip as well, although cleanup's `$PWD//abs` names nothing today. One helper, `respells`, holds the exact-match guard and both readings. devenv then skips cleanup, `devenv:files` runs and rewrites the state with the current spelling, and the next shell's cleanup runs normally. `devenv:files`'s own status doesn't pass `--state`, because skipping it would keep the old spelling recorded forever. The check fails closed: a state file that jq can't read as exactly one `{"managedFiles": [<string>...]}` also exits 0, since it can't be checked. A missing state file is fine, because cleanup has nothing to remove then.
   *Alternative:* always skip cleanup in a session. Rejected: `devenv:files` would then rewrite the state without the orphans, and a later terminal shell would never remove them.
5. **Only `devenv:files`' status relinks.** `devenv:files:cleanup` runs before `devenv:files`. Its status is `--check-only --state`: it never writes, and it skips cleanup while any protected link is stale (a real file doesn't count) or the state check marks a skip. `devenv:files`' status then tries the atomic relink. If that succeeds, `devenv:files` runs, finds the links current and rewrites the state. If not, it is skipped too, and the notice reports the stale files. Every write near a protected path then happens in one place.
   *Trade-off:* when the session's relink succeeds, cleanup was already skipped in that shell, and `devenv:files` rewrites the state without the old entries. So links orphaned by that same update are never removed. With devenv 2.4, cleanup only removes entries missing from the current list, so it can't touch a current protected file except through decision 4. Skipping it on staleness alone is therefore extra caution, and it costs that orphan cleanup.
6. **The notice names the eval cache.** `coldlogic:generated-files-stale` keeps its text and adds: if a terminal shell doesn't fix them, its evaluation may be stale, so run `devenv shell --refresh-eval-cache` there. That is the derekjw.com case in #68, where a terminal shell kept relinking the pre-#69 settings.

## Risks / Trade-offs

- **[Sandbox semantics unverified]** No one has yet checked whether Seatbelt denies the rename onto a denied path or the create of the temporary link. → It doesn't matter for safety: if the rename is allowed, the link is current; if anything is denied, the old link stays. Task 3.1 checks the real behaviour in a session.
- **[Claude Code's revert tracking]** #68 showed that once a session sees a protected path change, Claude Code keeps putting it back the way it recorded it. A rename the sandbox allows is still a change, and Claude Code might revert it to the old link. → That leaves a stale but present link, which the notice reports. Task 3.1 watches for it.
- **[Stray temporary link]** A shell killed between `ln` and `mv` leaves `.settings.json.coldlogic-relink.<pid>` beside the file. → It is a harmless dangling-or-store link. In relink mode the script sweeps every protected path, a current one included, before checking it. It removes a `.<base>.coldlogic-relink.<pid>` link only when all of these hold: the link points into `/nix/store`, `<pid>` isn't its own, `kill -0` reports "No such process", and `find -mmin +1` says the link is more than a minute old. A concurrent shell's temporary link is still in use. The sandbox can also refuse to signal a running process, so an EPERM keeps the link too. The age check covers a reused PID and a link made just before its owner's rename. On failure, the script removes the temporary link only if this run made it.
- **[Damaged checkouts stay damaged]** The fix stops new deletions. It doesn't restore a link a session already removed. → The notice already tells the developer to run a terminal shell, and Claude Code needs a session restart afterwards (#68).

## Migration Plan

No migration. Projects pick it up on their next lock bump. Rollback is reverting the commit; the old probe comes back with its bug.
