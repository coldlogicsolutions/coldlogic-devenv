# Design

## Context

See proposal.md for why. The session sandbox (`devenv.nix`, `sandbox.filesystem.denyWrite`) protects `<main>.worktrees/*/.git`, `.claude/settings*.json`, `.claude/hooks` and `.claude/skills` in sibling worktrees, and Claude Code itself protects the main checkout's `.git/config` and `.git/worktrees/*`. Seatbelt can't allow a delete while denying the write, so `git worktree remove` from a session fails partway (#73's `agent-a240a855d2d07281b`). Those rules stay.

What runs outside the sandbox without Derek: Claude Code hooks ("Hooks run outside the Bash sandbox", code.claude.com/docs/en/self-hosted-environments-configuration) and devenv tasks in a terminal shell. The module already uses both: `claude.code.hooks.coldlogic-guard` (PreToolUse) and `tasks."coldlogic:*"` before `devenv:enterShell`. devenv's `claude.code.hooks.<name>` option has only `hookType`, `matcher`, `command`, `name` and `enable`; it has no `async` or `timeout`.

Worktrees come from three places: the `WorktreeCreate` hook (`<main>.worktrees/<name>`, agents with `isolation: worktree`), Claude Code's own `.claude/worktrees/<name>`, and the lead's `git worktree add --detach|--no-track` for teammates (also `.claude/worktrees/`). PRs are squash-merged (`gh-app pr merge --auto --squash`), so a merged branch's HEAD is usually not an ancestor of `origin/main`. Claude Code already removes an agent worktree that has no changes when the agent ends; what is left behind has commits.

Derek's manual script (`prune-worktrees.sh`, 2026-11-11) covered 15 worktrees across both locations, one half-deleted (`rm -rf` after `remove` failed), `git worktree prune`, and 21 branches, several with no worktree left (`worktree-agent-a2a2f30589cd59eaf`, `ci/install-nix-action-v31.11.3`).

## Goals / Non-Goals

**Goals:**
- Merged worktrees and branches disappear with no step from Derek, in every project on the module.
- No path that can lose work: dirty, unmerged, or in use is kept, and every removal is the non-forcing git one.
- A session never waits on it and never sees output from it.

**Non-Goals:**
- Deleting remote branches (GitHub deletes the head branch on merge where the repository is set to).
- Worktrees outside the two known locations, and other repositories' worktrees.
- Loosening the sandbox, or letting a session's Bash remove worktrees.
- A notice of pending cleanup (the issue's idea): there is nothing for Derek to do with it.

## Decisions

1. **One packaged script, tested at build time, like session-relink.** `packages/prune-worktrees.sh` becomes `coldlogic-prune-worktrees` through `packages/prune-worktrees.nix`: `writeShellApplication` with `runtimeInputs` git, coreutils, findutils, jq, lsof and procps' `ps` (nixpkgs' on Linux only; on macOS the system ones, the script appending `/usr/sbin` to PATH for `lsof`) and the module's `gh-app`, and a `runCommand` that runs `packages/prune-worktrees-test.sh` against the raw script, referenced from the wrapper's text so the build depends on it. `devenv.nix` imports it beside `session-relink`. The gate's `build: shell` step runs the tests and shellcheck covers both scripts, with no change to `scripts/check.sh`.
   *Alternative:* a devenv task body inline in `devenv.nix`. Rejected: it can't be tested without a session, and the hook needs the same code.

2. **Usage.** `coldlogic-prune-worktrees [--dry-run] [--background] [--hook] [--session-dir <dir>] [--idle-minutes <n>]`, run from anywhere in the repository. It finds the repository with `git -C <dir> rev-parse --path-format=absolute --git-common-dir` (`<dir>` is the session dir, else `$PWD`), and the main checkout as the common dir's parent, so a run from a linked worktree acts on the same set. Not in a git repository, or a bare one: exit 0. `--hook` reads Claude Code's hook input from stdin and takes `.cwd` as the session dir (falling back to `$CLAUDE_PROJECT_DIR`, then `$PWD`). `--background` re-executes the script with `nohup`, stdin from `/dev/null` and stdout and stderr appended to the log, in the background, and exits 0 at once. Every file descriptor Claude Code holds is then closed, so the hook returns in milliseconds and the prune outlives the session. `--idle-minutes` takes at most 6 digits with no leading zero (`0` itself aside), else exit 2: bash arithmetic reads `010` as octal 8 and fails on `08` under `set -u`, and the cap keeps minutes times 60 far from overflow. A local variable never takes the name of a global that `say` or `keep` uses (`log`, the log file's path): bash's dynamic scope would send their lines there. Numbers read from outside (file mtimes) are checked as digits and taken with `10#`. Every array expansion is guarded (`${a[@]+"${a[@]}"}`), since bash before 4.4 calls an empty array unbound under `set -u`; a test checks the script has no other kind.
   *Alternative:* `"async": true` on the hook, which Claude Code supports for command hooks. Rejected: devenv's option has no field for it (adding it means overriding the generated `hooks` JSON beside `claude.nix`'s), an async hook's output is delivered to Claude on the next turn, and the docs don't say whether an async hook survives the session exiting. Detaching works for the shell task too, and keeps SessionStart quiet: its plain stdout would be added to Claude's context.

3. **Candidates.** `git worktree list --porcelain` gives each worktree's path, HEAD, branch, `locked` and `prunable`. A candidate is not the main checkout, not locked, and has a real path under `<main>.worktrees/` or `<main>/.claude/worktrees/` (compared after `realpath`, so `..` or a link can't escape). Branch candidates are `git for-each-ref refs/heads`, minus any branch a worktree has checked out (including the main checkout's, and one a worktree is rebasing or bisecting, named in its git dir's `rebase-merge/head-name`, `rebase-apply/head-name` or `BISECT_START`: such a worktree shows a detached HEAD, and `git branch -d` treats the branch as checked out too), minus every long-lived branch. Which branches worktrees hold is read once per `git worktree list --porcelain` read (each worktree's git dir found from its `.git` with builtins) and reused; it is read again after each removal and just before each branch deletion, so a worktree made on a branch mid-run keeps it. When the list can't be read, no branch is deleted. A branch is long-lived when it is the default branch (`origin/HEAD`'s target, else `main`) or is named, in any case (the name is lowercased before the match: with `core.ignorecase` on macOS, `Staging` can be the same ref as `staging`), `main`, `master`, `develop`, `dev`, `staging`, `production`, `prod`, `release/*` or `hotfix/*`. A long-lived branch at the exact head of a merged promotion PR (`staging` into `main`) would otherwise pass decision 5. It is kept and the log says which rule kept it. An upstream doesn't make a branch long-lived: any other branch is deleted only as the exact head of a merged PR (or with commits such a PR contains), so its work is in main, the remote copy stays, and the log has the command that restores it. The session dir and `$PWD` are resolved with `realpath -m` before the script changes to the main checkout, so a relative `--session-dir` means what it did where the run began.

4. **Clean.** `GIT_OPTIONAL_LOCKS=0 git -C <wt> status --porcelain=v1 --ignored=matching --untracked-files=all` must list nothing but ignored paths (`!! `), and each of those must be regenerable or generated. At the worktree's top only: `target`, `node_modules`, `.mcp.json`, `.pre-commit-config.yaml` and `.claude/settings.json` (build output, dependencies, devenv's generated files); `result` and `result-*` only as a link whose target starts with `/nix/store/` (Nix's out-links), so a real `result-2026-q3/` directory keeps the worktree; and OpenSpec's files, which the module's `coldlogic:openspec-files` task generates with `openspec init --tools claude` as real directories, not links: a `.claude/skills/openspec-*` directory only when it holds just a regular `SKILL.md`, and `.claude/commands/opsx` only when it holds just regular `*.md` files (checked against this repository's generated copies on 2026-11-11). These match the whole entry only: a path inside a `result-*` or `.claude/skills/openspec-*` directory (`result-data/.env`), listed because the directory isn't ignored as a whole, isn't that entry and keeps the worktree; the any-depth names below are matched on the whole last component the same way. A `sub/target` or `sub/node_modules` could be anything, so it keeps the worktree. `.devenv.flake.nix`, devenv's one generated root file besides `devenv.lock` (its template ignores `.devenv*`), counts at the top or beside a nested `devenv.nix`; any other `.devenv.*` name is unknown and keeps the worktree. At any depth: `.direnv`, `__pycache__`, `.DS_Store`, a `devenv.lock` beside a `devenv.nix`, and `.devenv`, but a `.devenv` only when its state dirs (`state`, `profiles/*/state`), where devenv services keep their data (a postgres cluster), hold nothing but devenv's and this module's bookkeeping: `tasks.db` (and its `-wal`, `-shm`, `-journal`, `.init.lock`), `files.json`, `prek`, `coldlogic-freshness` and `coldlogic-openspec`, as checked in this repository's `.devenv/profiles/developer/state` on 2026-11-11. The rest of `.devenv/profiles/<p>/` (`shell-*.sh`, `gc`, `nix-eval-cache.db`, `bootstrap`, `run`, `profile`) is cache. `git worktree remove` deletes ignored files without asking, so any other ignored file (`.env`, `.dev.vars`, `devenv.local.nix`, a service's data, anything unknown) keeps the worktree, logged with its path. So does an index entry marked skip-worktree or assume-unchanged (`git ls-files -v`: tag `S`, or lowercase), since `status` doesn't show its changes and `remove` would drop them. `--ignored=matching` lists an ignored directory once rather than each file in it. A path status quotes (unusual characters) doesn't match the list, so it keeps the worktree too. `GIT_OPTIONAL_LOCKS=0` stops `status` refreshing the index, which would also reset the idle clock (decision 6). It also checks `rebase-merge`, `rebase-apply`, `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD` and `BISECT_LOG` under `git rev-parse --git-dir`, since a stopped rebase can have a clean tree. A worktree whose status fails (a broken `.git`) is kept and logged; `git worktree prune` deals with ones whose directory is gone.

5. **In main.** Base: `refs/remotes/origin/HEAD`'s target, else `refs/remotes/origin/main`. If neither exists, nothing is in main. A worktree's HEAD C is in main when `git merge-base --is-ancestor C <base>`. Otherwise it needs a PR merged into the default branch (`baseRefName` equal to it; a PR into `staging` doesn't count): on a branch, one whose `headRefName` is that branch and whose `headRefOid` is C or contains C (`merge-base --is-ancestor C <oid>`, which fails, and so keeps it, when the commit isn't local); detached, one whose `headRefOid` is exactly C. The merged PRs come from one call per run, made from the main checkout with `timeout 15` when the first candidate needs it: `gh-app pr list --state merged --base <default> --json headRefName,headRefOid,baseRefName --limit 200`, matched locally (the `baseRefName` is checked again in `jq`). A PR older than the newest 200 no longer counts, so such a worktree stays; when the call returns exactly the limit, that is logged (once, as a kept reason). When the call fails, or `gh-app` is missing, nothing counts as merged by a PR for that run. This check runs first for each worktree, before the clean and in-use checks, so an unmerged worktree never costs a `status` or `ls-files` scan; the ancestor test is local, and the one `gh-app` call is still made only when a candidate needs it.
   A branch with no worktree is held to more: it is deleted only when it is, name and commit, the exact head of a PR merged into the default branch (`headRefName` and `headRefOid`). Ancestry of main isn't enough, since a lagging `staging` or release branch is an ancestor of main and still in use. A branch whose worktree this run removed is held to nearly the same (decision 7).
   No `git fetch`: the remote may be SSH through 1Password, which would ask for approval on every session start, and the squash-merge case needs GitHub anyway. Sessions fetch often enough that the local `origin/main` is close.
   *Alternative:* compare trees or patch ids against main to detect a squash offline. Rejected: a squash of several commits has no matching patch id, and a tree match says nothing about later commits.

6. **In use.** Three checks, any of which keeps a worktree:
   - **The session's own directory**: the session dir and `$PWD` are each matched against every candidate; a candidate containing either is kept.
   - **Processes**: one `timeout 20 lsof -a -d cwd -Fn` call lists the working directory of every process `lsof` can see, whoever's it is (a shell another account has in the worktree counts; one `lsof` can't see is missed, which the idle period still covers). A candidate containing one is kept. That covers a Claude Code session started inside a worktree, a terminal shell there, and a running build. The same call runs again right before each `git worktree remove`, since the first can be minutes old after a slow `gh-app` call, and at that point the worktree's HEAD and its branch ref are read again: if either moved from what was checked, the worktree is kept, and the removal's log line and restore command name the re-read commit. The clean check (decision 4, ignored files included) runs again then too, so an ignored `.env` written mid-run keeps the worktree. `in_use` and the re-check share one `lsof` matcher. When `lsof` fails or times out, every candidate is kept for that run (fail closed).
   - **Idle period** (default 360 minutes, `--idle-minutes`): the newest mtime among the worktree's git dir (`git rev-parse --git-dir`) and its `HEAD`, `index`, `logs/HEAD` and `ORIG_HEAD`, the worktree's top directory, and `.devenv`, `.devenv/state`, `.devenv/profiles/*` and `.devenv/profiles/*/state` in it, must be older than the period. The profile directories are what moves: checked on 2026-11-11 (task 2.4), `devenv shell --quiet -- true` in a worktree on the developer profile left `.devenv` unchanged and created no `.devenv/state`, because with a profile devenv's dotfile dir is `.devenv/profiles/<profile>` and its state `.devenv/profiles/<profile>/state`; both of those moved on every entry (the `run` link and `tasks.db` are rewritten). `.devenv` and `.devenv/state` stay for a shell without a profile. That catches what `lsof` can't: a teammate or subagent whose Bash shells come and go, and whose worktree no process holds between calls. Every commit, checkout or `devenv shell` in the worktree resets the clock. A fresh worktree created at `origin/main` (which the ancestor check alone would call merged) is protected by its git dir's creation time. For a branch candidate, the clock is its reflog (`logs/refs/heads/<branch>`), else the ref file or `packed-refs` time.
   *Alternative:* only the session's cwd and `lsof`. Rejected: agents and teammates in worktrees have no long-lived process there, and a just-created worktree at `origin/main` looks merged.

7. **Removal.** For each worktree that passes: `git worktree remove <path>` (no `--force`). On success, if it had a branch, the branch goes too unless another worktree holds it (the same set as decision 3, read again after the removal, the main checkout's included, minus the removed worktree), it is long-lived (decision 3), its name has a `]` (`git config --remove-section branch.<name>` can't address such a section, checked on git 2.56, while `"` works and `\` isn't a valid branch name; deleting the ref would leave its config behind), or no merged PR covers it: it must be the exact head of a PR merged into the default branch, or have commits past `origin/main` that such a PR on that branch contains. A worktree on `main`, or on a `staging` that trails `origin/main`, passes the ancestor check and goes, but its branch stays. A worktree, on a branch or detached, is kept, before the clean check and again just before the removal, when a commit in its HEAD reflog (`git -C <wt> reflog --format=%H HEAD`, fed to `git rev-list --stdin --not --all`) is held by no ref and no merged PR's head, or when the reflog can't be read (git reads a reflog it can't open as empty, so an unreadable `logs/HEAD` counts too): the reflog goes with the worktree and may be all that holds work abandoned there. A worktree on a branch is checked too: a commit made detached and left by switching back to the branch is in no branch's reflog. A merged PR's head holds its commits, as its work is in main: a branch reset back from its squash-merged head leaves that head in the HEAD reflog only. Those heads are the merged PRs' `headRefOid`s this clone has (`git cat-file --batch-check`, once per run), fed as `^<oid>` lines to a second `rev-list --stdin --not --all` over what the first left; a head the clone hasn't got would fail `rev-list`, so it is left out. The deletion is `git update-ref -d refs/heads/<branch> <checked HEAD>`, which deletes only if the branch still points there, then `git config --remove-section branch.<branch>`, ignoring "no such section". A failed remove is logged and the rest is left. After all worktrees, `git worktree prune`, but only when every worktree whose directory is gone (`prunable`) lies under the two roots: it unregisters every such worktree, and a missing one elsewhere (an unmounted disk, a repository moved by hand) isn't this command's to drop. It also needs the root holding each such worktree, and the worktree's parent directory, to exist (`test -d`, not only `realpath -m`): a root that is a link to an unmounted volume makes every worktree on it look gone. The root must also be on the main checkout's device (`stat -c %d`, else BSD `stat -f %d`, of its real path), since a volume can unmount and leave its mount point behind as an empty directory, which `test -d` passes. Otherwise it is skipped, and logged, until that one is dealt with. A `prunable` worktree counts as gone only when nothing is at its registered path: git also calls one prunable whose `.git` file alone is missing, and then prune is skipped and logged. A worktree moved by hand does look gone, yet its admin dir (`.git/worktrees/<id>`, found by its `gitdir` file) holds its index, HEAD and HEAD reflog, which prune deletes. So prune is also skipped, and logged with `git worktree repair` as the fix, when a gone worktree's admin dir can't be found, its index has staged changes (`diff-index --cached` against its HEAD), its HEAD is held by no branch, tag or remote branch (not `--all`, which counts every worktree's HEAD, its own included), or its HEAD reflog has a commit no ref or merged PR's head holds, on a branch or detached (checked on git 2.56: a moved worktree and one with only its `.git` deleted both show `prunable gitdir file points to non-existent location`). Then branch candidates (decision 5), held to the same `]` rule, each kept one logged with its reason (the default branch's "it's the default branch" too; a branch a worktree has checked out gets no line, its worktree's covers it), via `update-ref -d` and the config section. Removals happen in the main checkout (`git -C <main>`), never inside the worktree being removed. `--dry-run` prints `worktree <path> (<branch>)` lines, each followed by `branch <name>` when the real run would delete that branch with it (judged as if the worktree were gone), and `branch <name>` lines for branches without a worktree, and skips every write, the lock and the stamp included.
   *Alternative:* `git branch -D`. Rejected only for the race: `update-ref -d <ref> <old>` is the same deletion with a compare. The config section removal is what `branch -D` also does.

8. **Triggers.** In the developer profile:
   - `claude.code.hooks.coldlogic-prune-worktrees` (`SessionStart`) and `claude.code.hooks.coldlogic-prune-worktrees-stop` (`Stop`), each `command = "${prune}/bin/coldlogic-prune-worktrees --hook --background"`. SessionStart catches what merged since the last session; Stop catches merges during a long-lived session (Derek's lead sessions run for days). The rate limit (decision 9) makes Stop cost one `stat` and a fork per turn at most: with `--background`, before forking git or jq, the script finds the common dir from the session dir's `.git` with bash builtins (a directory, or a `gitdir:` file and its `commondir`), and exits when the stamp there is under 10 minutes old. With `--hook` the run acts on the input's `.cwd`, which only `jq` reads properly, so `$CLAUDE_PROJECT_DIR` stands in for it only when a builtin match finds a plain `.cwd` inside it, or the input has no `cwd` at all (the run then falls back to the project dir too); a `.cwd` elsewhere, in another repository say, takes the full lookup, which reads that repository's stamp. Anything unusual falls through to the full lookup.
   - `tasks."coldlogic:prune-worktrees"`, before `devenv:enterShell`: exits 0 when `CLAUDECODE` or `CI` is set, else runs `coldlogic-prune-worktrees --background --session-dir "$DEVENV_ROOT"`, then `exit 0`. Inside a session the sandbox would deny the removals, and the hooks cover it.
   The guard hook and the permission rules are untouched: the prune never goes through the Bash tool.
   *Alternative:* `SessionEnd`. Rejected: Claude Code gives it a 1.5 s timeout by default, and a session's own worktrees would still be inside the idle period then.

9. **Lock, stamp, log.** In the git common dir, which every worktree shares: `coldlogic-prune.lock/` made with `mkdir` (atomic; the worktree list is read again once it is held, as the first read, which only finds the main checkout, may predate another run's removals), holding a token unique to the run (`<pid>-<nanoseconds>`) and, on a second line, the run's process start time tagged with its source: on Linux `ticks:<n>`, field 22 of `/proc/<pid>/stat` (clock ticks since boot, read after the last `)` so a command name with spaces or parentheses can't shift it, and unlike `ps`'s `lstart` not recomputed from a drifting boot time), elsewhere `lstart:<ps -o lstart= -p <pid>>`. Start times are compared only when their tags match. If the owner can't be written after the `mkdir` (a full disk, say), the run removes the lock, logs it (as the `lock-write` kept reason, so once until it changes, like the over-an-hour skip) and exits 0, rather than leave an ownerless lock that blocks runs for an hour. A lock whose PID `kill -0` reports as "No such process", whose PID's process now has another start time than recorded (the PID was reused, after a reboot say), or that names no PID (a run died between `mkdir` and writing it) and is older than an hour, is taken over. A live owner's lock never is, however old: a slow run is still a run. A run skipped for a lock over an hour old logs that, once until it changes, so a stuck run isn't silent. `ps` is the system one on macOS and nixpkgs' `procps` on Linux, where it is only the fallback for a missing `/proc`. Taking over happens under a second `mkdir` lock, `coldlogic-prune.lock.takeover/`, and the lock is judged stale again once that is held, so two runs can't both replace the same lock; a takeover lock over a minute old (its taker died: taking over takes milliseconds) is removed. The exit trap removes the lock only while it still holds this run's token, so a run whose lock was taken over never removes its successor's. `coldlogic-prune.stamp` is touched when a `--background` run launches, before it detaches, and again when a run completes; a `--background` run within 10 minutes of it exits before detaching, so the hooks and shells that start while a run works don't each start another. Manual and `--dry-run` runs ignore the stamp. `coldlogic-prune.log` gets a timestamped line per removal, with the commit and the command that restores it (`git worktree add <path> <sha>`, `git branch <name> <sha>`, path and name quoted with `printf %q`, so a pasted line is safe and works for a name with a space or `$( )`), and per kept candidate with its reason, but a reason only when it differs from the last run's, and once per run (a branch can be kept after its worktree's removal and again by the sweep of branches without one): `coldlogic-prune.kept` holds the last run's reasons (`<key>\t<reason>`, written atomically at the end), so an hourly run over the same worktrees adds nothing, and a gh-app or `lsof` failure is logged once until it changes. At the end of a run the log keeps every removal line and the last 1000 others. Nothing goes to the terminal or the session; a dry run prints every reason to stderr.

10. **Tests** (`packages/prune-worktrees-test.sh`, `bash <test> <script>`): each case builds a throwaway repository in `mktemp -d` with a bare `origin`, a main checkout and worktrees in both locations, sets `GIT_CONFIG_GLOBAL=/dev/null` and a fixed identity, backdates activity with `touch -d`, and puts stubs on `PATH`: a `gh-app` that answers from a fixture file or fails, an `lsof` that prints a given cwd or fails, and a `ps` that prints a given start time, plus a `stat` wrapper that reports another device for one path, and logging `git` and `jq` wrappers for the fast path and the check order. `COLDLOGIC_PRUNE_PROC` points the `/proc` read at a missing directory, so the `ps` stub is used on every platform, or at a fake `/proc/<pid>/stat` for the Linux case. Test worktrees' branches are made with `--no-track`, as sessions make them. One case per scenario in the spec. The `gh-app` and `lsof` stubs can also run a command first, which is how the tests change things after the checks: a branch moved (not deleted), a commit made, a process started, an ignored `.dev.vars` written, a worktree added on an orphaned branch, and an untracked file written into the worktree (kept, so the case fails if `git worktree remove` gets `--force`). They need no network and no credentials, so they run in the Nix build sandbox.

## Risks / Trade-offs

- [A teammate in a clean worktree with no commits, which has only read files for longer than the idle period, loses its worktree mid-task] → The default period is 6 hours. Claude Code's own teammates and subagents touch `.devenv` with each `devenv shell`. Removal needs a clean tree, so no work is lost, only the checkout. The same goes for a clean worktree with no commits of its own that only an editor or an in-process subagent is using: neither has its working directory there nor runs git or `devenv shell` in it, so after the idle period nothing marks it as in use, and it is removed under them.
- [A worktree merged with a merge commit is removed although `origin/main` is stale] → Can't happen: being an ancestor of an older `origin/main` means being in main.
- [`gh-app` installation doesn't cover a project's repository] → The one call fails and only the ancestor check applies, so squash-merged worktrees in that project stay, and no branch without a worktree is deleted. Logged once, until it changes.
- [A run that dies holding the takeover lock while another breaks it after a minute] → Both could then take over. The takeover lock is held for milliseconds, so this needs a crash in that window and a second run a minute later, and the worst case is two runs at once, each of whose removals is still the non-forcing, compare-and-delete kind.
- [A merged worktree with an ignored file the list doesn't know (an IDE's directory, a local cache)] → It stays, logged with the path, until Derek removes it or the list grows. Keeping is the safe failure.
- [A merged PR's head commit is fetched nowhere locally, and HEAD is behind it] → `merge-base --is-ancestor` fails and the worktree is kept. Only equality or local ancestry counts.
- [A branch merged by fast-forward or a merge commit with no PR stays for good] → Accepted: without a PR naming it, nothing tells a finished branch from a lagging `staging`. Its worktree still goes, and the log says why the branch stayed.
- [A long-lived branch with a name outside the list (`qa`, `next`) is the exact head of a merged PR] → It is deleted locally. Only its exact merged head goes, so nothing is lost: the remote copy stays and the log has `git branch <name> <sha>`.
- [A volume unmounts and leaves its mount point as an empty directory on the main checkout's device, holding the root] → The root then exists and is on the same device, so `git worktree prune` runs and unregisters the worktrees that were on the volume. Only git's registration is lost; the files are on the volume, and `git worktree repair` or `git worktree add` brings them back once it is remounted.
- [A root that is legitimately on another device than the main checkout (a btrfs subvolume, a bind mount, a separate partition)] → Its gone worktrees are never pruned automatically: the run can't tell that device from an unmounted volume's mount point, and logs the skip once. Accepted, as keeping is the safe failure. The fix is by hand: `git worktree prune` from the main checkout, once the volume is known to be mounted.
- [A worktree on a branch that was rebased or reset, with no merged PR holding the old commits] → Its HEAD reflog has commits no ref holds, so it is kept, and logged once, until git expires those reflog entries (`gc.reflogExpireUnreachable`, 30 days by default, when gc runs) or it is removed by hand. Accepted: the branch's own reflog goes when the branch is deleted, so it can't stand in for the worktree's.
- [A worktree moved by hand with staged changes or abandoned commits, or one with only its `.git` file deleted] → `git worktree prune` acts on every gone worktree at once, so none is unregistered until that one is dealt with: `git worktree repair <new path>` for a moved one, or removing it by hand. Logged once. Accepted, as the alternative deletes its index.
- [A run hangs holding the lock] → Later runs skip until it exits; `gh-app` and `lsof` run under `timeout`, so a hang needs git itself to hang.
- [Cleanup lags a merge by the idle period] → Accepted: a merged worktree isn't in the way, and the guard is what keeps live work safe.
- [`lsof` on a machine with many processes is slow] → One call per run, in the background.
